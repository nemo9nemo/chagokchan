# 보안 위협 모델과 출시 검증 기준

결정일: 2026-10-07 / 상태: 구현 전 보안 설계

적용 범위: [개발 스택](technical-architecture.md), [로그인·권한](auth-and-permissions.md). 현재 실행 중인 앱이나 소스코드를 검사한 상태가 아니다. 아래 항목은 이 제품에서 예상되는 취약점과 예방·검증 기준이며, 실제 취약점 발견 보고서가 아니다.

## 보호할 정보와 신뢰 경계

보호 대상은 개인 목표·메모, 받은 칭찬 본문, 사람 연결 관계, 초대 비밀, 로그인 세션, 운영 자격증명이다. 공유판의 제목과 개수도 권한을 받은 지인에게만 제공한다.

브라우저의 사용자 ID·판 ID·입력·숨겨진 버튼은 신뢰하지 않는다. 서버는 인증·입력을 검증하고, DB는 현재 사용자와 객체 권한·상태를 다시 확인한다. 지인에게 줄 공유 정보와 개인 원본을 별도로 저장한다. 운영 관리 키는 일반 사용자 요청 경로에서 사용하지 않는다.

UUID를 사용해도 객체 권한 검사는 필요하다. 권한 확인은 UI 버튼뿐 아니라 모든 관련 API와 DB 경로에 적용한다. [OWASP 객체 권한 취약점](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)

## API·DB 구현 규칙

1. 일반 요청의 DB 클라이언트는 publishable key와 검증된 사용자 JWT를 사용한다. service role/secret key로 사용자별 읽기·쓰기를 처리하지 않는다.
2. 각 읽기 정책과 쓰기 RPC는 활성 계정·현재 세션·객체 권한을 확인한다. actor_id·recipient_id·owner_id는 세션과 대상 판에서 정하고 입력으로 덮어쓰지 않는다.
3. 새 테이블은 RLS와 GRANT/REVOKE를 함께 정의한다. 새 함수는 기본 실행 권한을 회수하고 필요한 역할에만 허용한다. anon은 제품 데이터에 접근하지 못한다.
4. SECURITY DEFINER 함수는 최소 권한 소유자, search_path='', 완전한 스키마 경로, 매개변수 검증을 적용한다. RLS 우회 가능성을 전제로 함수 내부에서 권한을 검사한다.
5. 현재 세션 확인은 비공개 함수가 auth.sessions와 현재 JWT의 session_id·사용자를 대조한다. auth 스키마나 다른 사용자의 세션 목록을 공개하지 않는다.
6. 칭찬·회차·개수·완성·소식을 같은 트랜잭션에 넣는다. 외부 메일·푸시 전달은 이 트랜잭션에 넣지 않는다.
7. 요청 키는 작성자·작업 종류와 묶는다. 같은 키를 다른 내용·판에 사용하면 충돌로 거절한다. 권한이 해제된 뒤의 재시도에는 기존 결과를 무조건 공개하지 않고 현재 권한을 먼저 확인한다.
8. 요청 빈도 검사는 인증된 사용자 기준으로도 수행한다. DB 직접 호출은 앱의 IP 제한을 통과하지 않으므로 중요 사용자별 제한을 DB에서도 강제한다.

읽기 정책을 검사할 때 API의 정상 동작만 보지 않고 사용자 JWT로 Data API·뷰·RPC를 직접 호출한다. Postgres의 함수·뷰는 설정에 따라 RLS 동작이 달라질 수 있다. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 웹 입력과 세션 보호

모든 변경 요청은 JSON과 사용자 정의 CSRF 헤더를 요구한다. 서버가 현재 세션 또는 로그인 전 흐름에 묶어 서명한 CSRF 쿠키와 헤더 토큰을 검증하고, Origin을 정확한 앱 출처와 비교한다. Fetch Metadata도 보조 검사한다. 로그인 시작·OTP 발송·검증·로그아웃에도 적용한다. OAuth GET 콜백은 일반 쓰기 API와 분리하고 PKCE·인증 흐름 검증으로 보호한다.

제품 데이터를 바꾸는 GET은 만들지 않는다. CORS에서 임의 출처와 자격증명을 허용하지 않는다. SameSite=Lax만으로 CSRF 대응이 끝났다고 보지 않는다. [OWASP CSRF 예방](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

목표 제목은 80자, 칭찬·메모는 1,000자, 일반 JSON 본문은 32KB까지로 시작한다. 서버 검증을 기준으로 삼고 조회는 페이지당 최대 50건으로 제한한다. SQL은 바인딩된 매개변수를 사용하며 사용자 입력으로 SQL·정렬 컬럼·리다이렉트 주소를 구성하지 않는다.

칭찬 문구는 일반 텍스트로 표시한다. 첫 버전에 HTML·Markdown 실행·첨부 업로드·외부 이미지 URL을 넣지 않는다. CSP는 nonce 기반으로 구성하고 Turnstile 등 필요한 출처만 허용한다. frame-ancestors 'none', X-Content-Type-Options: nosniff, 운영 HTTPS의 HSTS, 초대·인증 화면의 no-referrer를 적용한다. CSP가 필요한 인증 화면을 막지 않는지 스테이징에서 확인한다.

HttpOnly는 스크립트가 토큰을 읽는 것을 줄이지만 XSS가 인증된 요청을 보내는 것까지 막지는 못한다. 출력 처리·CSP·권한 확인을 함께 적용한다.

## 초대·인증 남용과 장애 처리

초대 링크의 비밀은 URL fragment에 두어 일반 서버 요청 URL에 전달하지 않는다. 초대 코드는 연결 대기 정보를 만드는 용도이며 최종 수락·판 권한을 대신하지 못한다. 사용 전·후 비밀을 로그에 남기지 않는다.

이메일 존재 여부를 발송 응답으로 알려 주지 않는다. 오류도 가능한 범위에서 같은 형태로 안내한다. OTP 재사용·오입력·만료와 Google 인증 취소를 정상 흐름으로 처리한다.

Supabase Auth의 공개 인증 엔드포인트에는 자체 CAPTCHA·요청 제한을 적용한다. 앱 API의 Upstash 제한만으로 직접 Auth 호출이 차단된다고 가정하지 않는다. Upstash 장애 시 OTP 발송·초대·칭찬 쓰기는 503으로 잠시 거절하며, 인증·권한이 유효한 읽기는 계속 제공한다. [Auth 요청 제한](https://supabase.com/docs/guides/auth/rate-limits), [Upstash 제한기](https://upstash.com/docs/redis/sdks/ratelimit-ts/overview)

IP 식별자는 배포 플랫폼이 제공하는 검증된 연결 정보를 사용한다. 사용자가 보낸 임의 헤더를 신뢰하지 않는다. 이메일·IP 기반 제한 키는 서버 비밀을 사용한 HMAC으로 만들어 외부 저장소에 원문을 남기지 않는다.

## 로그·운영 접근·백업

- 운영 로그는 요청 ID, 내부 사용자 ID, 작업 종류, 성공·거절 코드, 처리 시간 위주로 남긴다. 칭찬 본문·개인 메모·이메일·인증번호·초대 비밀·Cookie·Authorization은 수집하지 않는다.
- 오류 추적 도구를 연결할 때 URL·요청 본문·헤더를 필터링한다. 접근·오류 로그와 권한 감사 기록은 30일 보관을 초기 기준으로 삼는다.
- 운영 서비스 관리자에는 MFA를 적용한다. 읽기·지원에 필요 없는 관리자를 늘리지 않고 접근자를 기록한다. 사용자의 개인판을 읽는 제품 운영자 UI는 만들지 않는다.
- DB 관리 자격증명은 여전히 강한 권한을 가진다. 이 제품을 종단간 암호화 서비스로 표현하지 않는다.
- 백업은 접근 가능한 운영자와 보관 위치를 제한하고 Git에 넣지 않는다. 운영 DB의 일일 백업 7일 보관과 복원 검증은 배포 문서를 따른다.

로그에서도 토큰·비밀·민감한 본문을 제외한다. [OWASP 로그 지침](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

위 항목은 구현 이후 실행할 테스트 요구다. 현재 문서 작성으로 테스트 통과나 보안 검증 완료를 선언하지 않는다. 출시할 때 결과와 미해결 항목을 릴리스 기록에 남긴다. P0·P1의 미해결 접근 통제·세션·기록 손상 문제는 출시를 막는다.

## 문제가 발생했을 때

1. 무단 접근이 가능한 기능·키를 차단하고 관련 세션을 폐기한다. 기록 쓰기 중단이 필요하면 유지보수 모드로 전환한다.
2. 민감한 본문을 추가로 수집하지 않고 요청 ID·작업·영향 대상과 시간 범위를 확인한다.
3. 키를 교체하고 원인을 수정한다. 데이터 복원은 손상 범위를 확인한 뒤 별도 환경에서 검증한다.
4. 같은 공격을 재현하는 테스트를 추가하고 스테이징에서 통과한 변경을 배포한다.
5. 영향 사용자에게 필요한 안내를 할 수 있도록 사고 기록을 남긴다.

사진 업로드·실시간 채널·웹 푸시·그룹·AI 연동은 현재 공격 표면에 포함하지 않는다. 도입할 때 파일 권한·서명 URL 만료·채널 재인증·그룹 역할·외부로 보내는 데이터 범위를 이 문서에 추가한다.

## 최초 가입 확인의 우회

Google·이메일 인증 성공과 active 앱 계정을 구분한다. UI의 성인 확인 버튼만 믿지 않고 bootstrap RPC에서 명시적 확인·현재 정책 버전·현재 Auth 세션과 진행 중 정리 표시를 검증한다. 미완료 Auth 사용자의 제품 조회·직접 RPC를 거절한다. 확인 시각은 서버 값이고 일반 계정 수정으로 변경하지 못한다.

만 19세 이상 자기 확인은 실제 나이·신원을 검증한 결과가 아니다. 확인 정보는 본인 응답에서만 제공한다. 미완료 Auth 정리와 가입 완료의 경합·실패 재시도·기존 계정 비삭제를 TC-AUTH-004에서 검증한다. [가입 정책](policies/audience-and-signup.md)
