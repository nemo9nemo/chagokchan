# W25 — 직접 입력하는 칭찬 태그

작성일: 2026-10-20 / W25-A~D 로컬 구현·검사 완료. PR/CI·병합은 GitHub 기록을 따른다. [실행 증거](../quality/reports/w25-custom-tags-check-2026-10-20.json)

사용자 요청: 태그는 사용자가 `#`부터 직접 입력하며 공백으로 나눈다. `#꾸준 `에서 공백을 입력하는 순간 `#꾸준`을 테두리가 있는 칩으로 만들어 입력칸 위 태그 영역으로 옮긴다. 여러 태그를 한 기록에 붙일 수 있다.

관련 기준: REQ-003·REQ-007 / POL-PRAISE-001·POL-PRAISE-002 / UI05(B05~B07). [진행표](../development/backlog.md)에서 기획과 구현 상태를 따로 관리한다.

## 화면과 의미

```text
태그 선택 (선택 사항)

[ #꾸준함  × ] [ #용기  × ] [ #배려  × ]

[ #태그를 입력하고 공백을 눌러 주세요             ]
#으로 시작해 공백으로 구분해 주세요. 최대 5개
```

- 위 영역은 **현재 칭찬 기록에 붙일 확정 태그**다. 칩 생성과 동시에 선택된 상태이며 다시 선택하는 단계는 없다. 최초 작성은 빈 영역에서 시작한다.
- 아래는 새 태그를 작성하는 입력칸이다. 확정된 부분만 입력칸에서 제거하고, 커서와 포커스를 입력칸에 유지한다. 추가된 칩은 입력 순서대로 오른쪽에 붙이고 폭이 부족하면 다음 줄로 감싼다.
- 기존 칩과 같은 둥근 테두리·색상 체계를 사용하고 삭제 버튼 `×`를 붙인다. 삭제 버튼은 키보드로 접근할 수 있고 이름은 “꾸준함 태그 삭제”처럼 읽힌다. 터치 영역은 44px 이상으로 확보한다.
- 칩을 삭제하면 현재 기록에서만 빠진다. 기존 기록의 같은 이름 태그를 변경하거나 지우지 않는다.
- 추천 목록·전체 사용자 공용 태그 목록·최근 태그 자동 노출은 이번 범위에 넣지 않는다. `#꾸준`은 `#꾸준함`으로 자동 교체하지 않고 입력한 이름을 사용한다.

## 입력과 확정

| 행동 | 결과 |
| --- | --- |
| `#꾸준` 입력 | 아직 입력칸에 남음 |
| 이어서 공백 입력: `#꾸준 ` | 위에 `#꾸준` 칩 추가, 입력칸은 비워짐 |
| 이어서 `#용기 ` 입력 | 기존 칩 옆에 `#용기` 추가 |
| `#꾸준 #용기 ` 붙여넣기 | 두 태그를 순서대로 확정 |
| `#꾸준 #용기` 붙여넣기 | `#꾸준`만 확정, 마지막 `#용기`는 입력칸에 남음 |
| 태그 입력칸에서 Enter | 유효한 마지막 태그를 확정하고 폼 저장은 실행하지 않음 |
| 마지막 `#용기` 뒤 공백 없이 저장 | 마지막 토큰까지 검증·확정한 동일한 목록으로 칭찬 저장 |
| 입력칸 바깥으로 포커스 이동 | 작성 중 텍스트 보존; 포커스 이동만으로 확정하지 않음 |
| 칩의 `×` 누름 | 해당 칩만 삭제 |

공백 구분에는 일반 공백·연속 공백·탭·줄바꿈·전각 공백 등 Unicode 공백을 포함한다. 쉼표는 구분자로 쓰지 않는다. 한글 IME 조합 중에는 토큰을 분리하거나 Enter로 저장하지 않는다. 조합이 끝난 뒤 확정된 입력값으로 한 번만 처리하며 조합용 Enter를 칩 확정 Enter로 중복 처리하지 않는다.

여러 토큰을 입력했을 때는 왼쪽부터 처리한다. 정상 토큰은 칩으로 이동하고 첫 오류 토큰부터 뒤의 원문은 입력칸에 남긴다. 예를 들어 `#꾸준 용기 #배려 `는 `#꾸준`만 확정하고 `용기 #배려 `를 보존한다. 저장 버튼에서 오류를 발견하면 칭찬 요청 전체를 보내지 않는다.

## 기획상 기본 제한과 오류

아래 수치를 실행 정책 `policies/app-policy.json`의 tags_per_praise_max·tag_codepoints_max에 반영하고 UI·API·DB·계약을 맞췄다. 고정 목록은 이전 요청 호환 전용이다.

| 항목 | 기획 기준 |
| --- | --- |
| 적용 대상 | 기존처럼 셀프 칭찬만 적용, 태그는 선택 사항 |
| 개수 | 기록당 0~5개 |
| 이름 길이 | `#` 제외, NFC 정규화 후 1~20 Unicode 코드포인트 |
| 허용 이름 | 한글 등 Unicode 문자·결합 문자·숫자·밑줄(`_`)·하이픈(`-`); 문자 또는 숫자가 최소 1개 포함 |
| 시작 문자 | 사용자가 입력한 `#` 필수; UI가 자동 보충하지 않음 |
| 저장·표시 | 저장값에는 `#`를 제외, 화면에는 `#`를 붙임 |
| 중복 | NFC 후 ASCII 영문 대소문자 차이를 무시해 중복 판정; 먼저 입력한 표기를 유지 |
| 순서 | 중복 제거 후 입력 순서 유지 |

오류 처리:

- `꾸준 ` → “태그는 #으로 시작해 주세요.” 입력을 보존한다.
- `# `·`##용기 `·허용되지 않은 문자가 있는 토큰 → 오류 안내, 칩으로 만들지 않는다. 연속 공백 자체는 무시한다.
- `#꾸준 #꾸준 ` → 칩 한 개만 유지하고 중복 토큰은 입력칸에서 제거한다. “이미 추가한 태그예요.”를 상태 메시지로 알린다.
- 21자 이상 → 자르지 않고 “태그는 20자까지 입력할 수 있어요.”를 표시한다.
- 여섯 번째 새 태그 → 기존 5개를 유지하고 남은 입력을 보존한다. “태그는 최대 5개까지 추가할 수 있어요.”를 표시한다. 중복 태그는 개수 초과로 취급하지 않는다.
- 공백만 남은 입력은 빈 입력으로 처리한다. `#`만 남거나 오류 토큰이 남은 상태의 저장은 막고 입력칸으로 포커스를 옮긴다.

추가·삭제·오류는 읽기 도구에 상태 메시지로 알린다. 입력칸이 비어 있을 때 Backspace로 앞 칩을 즉시 삭제하지 않는다. 색상만으로 상태를 구분하지 않는다.

## 저장·수정·실패

- 칩 확정은 작성 중 화면 상태 변경이다. 칭찬의 저장 성공 전에는 DB에 태그를 별도로 생성하지 않는다. 태그 수가 칭찬 개수·회차 완성·소식을 바꾸지 않는다.
- 수정 화면도 같은 입력기를 쓴다. 기존 태그를 칩으로 읽어오고 추가·삭제 후 전체 목록으로 교체한다. 상세·최근 기록에는 저장된 여러 태그를 모두 표시한다.
- 취소한 기록은 메모·실천일과 함께 태그도 지운다. 다른 기록의 태그에는 영향이 없다. peer 요청에 사용자 태그를 넣으면 기존처럼 거절한다.
- 저장 실패 시 메모·날짜·칩·미확정 입력을 보존한다. 공백 없는 마지막 토큰을 확정할 때 계산한 목록을 즉시 요청 본문에도 사용한다. React 상태 반영을 기다리지 않아 마지막 태그가 빠지는 일을 막는다.
- 응답을 잃은 요청의 재시도는 동일 요청 키와 동일한 정규화된 태그 배열을 재전송한다. 성공 여부가 불명확한 동안은 기존 재시도 절차대로 입력을 잠근다. 기존 저장 로직의 중복 방지·현재 세션·권한 검사를 유지한다.

## 데이터·API 전환 방향

변경 전 실행본은 `tag: 고정 코드 | null`이었다. W25에서 tags 배열을 추가하고 DB·RPC·응답 검증과 화면을 함께 연결했다. 기존 tag는 호환 투영으로 유지한다.

목표 계약은 `tags: string[]`다. 예: `{"message":"오늘도 해냈다","tags":["꾸준","용기"]}`. 생성 시 생략은 `[]`, 수정 시 생략은 유지·`[]`는 모두 삭제다. 새 계약에서 `null`은 허용하지 않는다. owner 응답은 항상 배열을 제공하고, contributor·보낸함에 개인 태그를 새로 노출하지 않는다.

전환은 추가형 마이그레이션으로 한다. 기존 마이그레이션을 수정하거나 DB를 초기화하지 않는다. 기존 코드 `consistency/courage/care/growth/rest`는 각각 `꾸준함/용기/배려/성장/쉼`의 1개 배열로 옮긴다. 기존 null·취소·peer는 빈 배열로 옮긴다. 기록 ID·개수·회차·시간은 보존한다.

W25-B에서 다음 호환 규칙을 구현·검증하고 실행 계약을 갱신했다.

1. 새 배열 열과 제약을 추가하고, 이전 앱이 계속 호출할 수 있는 RPC 경계를 유지한다. 배열 조회는 list_board_praises_with_tags로 분리하고 이전 list_board_praises의 응답 필드를 유지한다. 기존 `tag` 열·인자·응답을 같은 릴리스에서 제거하지 않는다.
2. 이전 입력 `tag`는 기존 5개 코드만 받아 0~1개 배열로 변환한다. `tag`와 `tags`를 함께 보내면 거절한다. 새 입력의 정규화·상한·중복은 API와 DB에서 같은 규칙으로 검사한다.
3. 과거 요청 키의 태그 포함/미포함 멱등 해시가 바뀌어 기존 재시도가 충돌하지 않게 호환 경로를 보존한다. 새 배열 요청은 정규화된 순서를 포함해 해시를 계산한다.
4. 배열을 기준으로 저장·조회·수정·취소하고, 구형 응답의 단일 `tag`는 호환 투영으로만 제공한다. 구형 수정이 새로운 여러 태그를 조용히 덮어쓰지 않도록 충돌을 반환한다. 태그와 무관한 구형 메모 수정은 배열을 유지한다.
5. 새 사용자 정의 태그 저장 이후의 화면 롤백은 기존 단일 태그 화면으로 단순 복귀하지 않는다. 배열을 보존하는 호환 화면 또는 쓰기 중단·수정 배포 절차를 먼저 준비한다. 구형 필드 제거는 후속 변경으로 분리한다.

사용자별 태그 사전 테이블은 추가하지 않는다. 태그는 각 칭찬 기록의 값이며 테마에 종속되지 않는다. 직접 DML·RLS·RPC 소유자·현재 권한·응답 제한·no-store 경계도 유지한다.

## W25-E 입력창 간격·정렬 보완 (2026-10-26)

사용자 화면 주석 4건에 따라 삭제 아이콘과 태그 글자의 간격을 줄이고, 확정 칩과 신규 입력칸 사이에는 공통 폼 간격 12px을 적용한다. 태그가 없으면 빈 칩 행을 숨긴다. 삭제 버튼의 공통 padding을 제거하되 44×44px 조작 영역은 칩 내부에 유지한다. 작성·수정에서 같은 TagInput 스타일을 사용한다.

태그 선택·메모와 자동 날짜/작성자는 텍스트와 배지를 각각 요소로 감싸 같은 flex 중앙 정렬·6px 간격·1.4 line-height로 배치한다. 입력 규칙·저장·집계·권한 정책과 API/DB 계약은 변경하지 않는다.

검증은 기존 check(린트·타입·unit·산출물), build:check와 diff 검토다. 743×784px 주석 화면 및 320px 줄바꿈·44px·라벨 정렬의 실제 브라우저 확인은 실행 여부를 따로 기록하고, TC-PRAISE-TAG-003·TC-UX-001의 기기 수락 완료로 간주하지 않는다.
