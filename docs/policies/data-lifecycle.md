# 데이터 생명주기·계정 정책

버전: 0.2.0 / 상태: MVP 개발 기준 / 기준일: 2026-10-07

기준 수치는 [정책 JSON](../../policies/app-policy.json)이다. 이 파일은 구현할 삭제·복구·계정 처리를 정한다. 공개 처리방침·이용약관은 운영 주체와 실제 제공자 설정을 확인해 별도로 작성한다.

## POL-ACCOUNT-001 — 최초 생성과 계정 수명

검증된 Supabase Auth UUID와 명시적인 성인 확인·현재 정책 버전으로 app_users·profiles 및 adult_confirmed_at·registration_policy_version을 한 트랜잭션에서 한 번 생성한다. 확인 시각은 서버 UTC다. [가입 기준](audience-and-signup.md) 사용자 입력 UUID와 이메일 문자열 비교로 다른 계정에 연결하지 않는다. 기본 프로필은 임시 닉네임·허용된 아바타 키로 만들고 사용자가 변경한다.

최초 생성 경로는 검증된 Auth 사용자·현재 세션을 요구하되 아직 없는 app_users를 전제로 처리한다. Auth 성공만으로 앱 계정을 자동 생성하지 않는다. 정리 표시가 없는 가입 확인 전에는 signup_required이며 일반 API는 생성된 active 계정을 요구한다. 초기화 실패는 같은 UUID로 재시도할 수 있고 기존 deleting 계정을 upsert로 active로 되돌리지 않는다. 재시도·재로그인은 최초 확인 시각·정책 버전을 덮어쓰지 않는다.

탈퇴 요청 이후 계정 복구·탈퇴 철회는 첫 버전에 제공하지 않는다. 탈퇴를 완료하고 다시 가입하면 새 UUID로 시작하며 과거 연결·권한·기록을 연결하지 않는다. 삭제 진행 중 로그인은 데이터 접근을 열지 않고 진행 안내로 처리한다.

Google·이메일 로그인 수단을 검증할 수 있으면 기존 계정 접근을 복구한다. 두 수단을 모두 잃으면 닉네임·기록 내용으로 계정을 넘기거나 운영자가 UUID를 병합하지 않는다. 이메일 변경·다른 이메일 identity의 수동 연결은 후속 기능이다.

## POL-ACCOUNT-002 — 세션과 재인증

보호 데이터의 읽기·쓰기는 JWT 확인과 함께 app_users.active 및 auth.sessions의 현재 session_id를 검사한다. 현재/전체 로그아웃을 구분하고 로그아웃 이후의 기존 JWT도 접근을 거절한다.

삭제 요청은 기존 사용자 UUID와 일치하는 10분 이내 재인증 grant를 요구한다. grant는 현재 세션·account.delete 작업에 묶이고 삭제 접수 트랜잭션에서 한 번 소비한다. Auth 세션 토큰·인증번호를 앱 테이블로 복제하지 않는다.

## POL-DELETE-001 — 목표 삭제·휴지통

일반 목표 삭제는 30일 휴지통이다. 삭제 트랜잭션에서 status=deleted, deleted_at=현재 UTC, purge_after=deleted_at+30일로 설정하고 판 권한을 회수한다. 일반 목표·판·칭찬·보낸함·소식 상세 경로는 해당 목표를 제공하지 않는다.

주인은 별도 휴지통 목록에서 목표 ID·본인 제목·revision·삭제 시각·복구 마감만 확인할 수 있다. purge_after 전까지만 복구하며 archived로 복구한다. 과거 contributor 권한은 복구하지 않는다. 복구한 목표는 명시적으로 resume해야 새 칭찬을 받는다.

기한이 지난 목표는 작업자가 목표/판 잠금을 확보해 최신 상태를 다시 검사한다. 최신 삭제 원장 기록을 먼저 보관한 뒤 소식·멤버·공유 프로필·칭찬·회차·판·목표를 의존 순서대로 제거한다. current_bunch_id 순환 참조를 먼저 해제한다. 관련 요청 결과와 감사 대상 참조도 정책에 맞춰 제거한다.

복구 요청과 정리 작업이 경합하면 같은 잠금에서 하나의 결과로 정리한다. 기한 후에는 작업자가 아직 처리하지 않았어도 복구를 거절한다. 정리는 기한 이후 24시간 내 완료를 목표로 하고 실패 시 재시도한다. 이 시간은 실행·측정 전의 운영 목표다.

## POL-DELETE-002 — 계정 탈퇴와 상대에게 보낸 기록

| 대상 | 목표·판 주인의 탈퇴 | 칭찬 작성자의 탈퇴 |
| --- | --- | --- |
| 본인 목표·개인 기록 | 휴지통 기간 없이 정리 대상 | 본인 소유 데이터 정리 |
| 본인이 받은 공유 칭찬 | 목표와 함께 삭제, 상대 보낸함에서도 제거 | 다른 사람에게 받은 기록이면 본인 목표와 함께 정리 |
| 타인에게 보낸 칭찬 | 해당 없음 | 본문·실천일·작성자 참조 제거, author_erased_at 기록 |
| 타인 판의 포도알 개수 | 판 자체 삭제 | 미취소·미제외 이벤트는 유지, 화면은 '삭제된 계정의 칭찬' |
| 연결·차단·멤버·초대·요청 | 종료 후 의존 순서 정리 | 같은 처리 |
| 소식 | 본인 소식 삭제, 타인 소식의 작성자·대상 포인터 정리 | 본문 복제 없이 원본 삭제 상태 반영 |
| 요청 결과·감사 | 본인 식별·본문 해시 제거 또는 해당 결과와 함께 제거 | actor 참조·input_hash 제거, 불필요한 식별 대상도 정리 |
| Auth 사용자·identity·세션 | 앱 정리 후 마지막에 제거 | 같은 처리 |

본문·작성자를 지운 기여 이벤트를 UUID 제거만으로 익명 데이터라고 표현하지 않는다. 수신자의 회차·개수 맥락을 유지하는 목적의 제한된 기록이며 목표 정리 시 함께 삭제한다. 새 칭찬의 actor는 필수이고 author erasure 전용 작업만 NULL로 바꿀 수 있다.

가입 미완료 정리는 app_users가 없는 Auth UUID만 대상으로 하며 기존 active/deleting 앱 계정을 삭제하지 않는다. 정리 대상 확정과 bootstrap을 같은 사용자 잠금으로 직렬화한다. account_deletion_requests에 user_id 없이 subject_auth_user_id와 작업 상태를 기록해 표시한다. pending/running/failed 표시가 먼저 기록되면 새 bootstrap을 거절하고, bootstrap이 먼저 완료되면 정리를 건너뛴다. 관리 Auth 삭제 호출은 일반 요청과 분리한다. 최종 세션·사용자 삭제가 실패하면 같은 표시와 작업을 재시도한다.

탈퇴 순서는 재인증 → app_users.deleting·deactivated_at·삭제 요청을 한 트랜잭션에 기록 → 모든 제품 접근 차단 → Auth 세션 폐기 시도 → 최신 삭제 원장 확보 → 본인/상대 기록 정리 → 앱 FK 의존 제거 → Auth 삭제 → 작업 완료다.

접근 차단은 접수 트랜잭션 커밋부터 적용한다. Auth API 실패가 있어도 deleting 상태로 읽기·쓰기를 차단한다. 데이터 정리는 24시간 이내를 운영 목표로 하고 실패 시 checkpoint부터 재시도한다. 탈퇴 job은 pending/running/completed/failed 상태와 오류 코드만 기록한다.

개인화된 FK를 무조건 CASCADE로 삭제하지 않는다. 작성자 참조를 NULL로 바꾸는 것만으로 본문 파기를 완료한 것으로 판단하지 않는다. 작업 완료 조건에는 본문·프로필·세션·연결·공유 권한 정리가 포함된다.

## POL-DELETE-003 — 보관과 복원

| 데이터 | 초기 보관 기준 | 정리 조건 |
| --- | --- | --- |
| 성인 확인 시각·버전 | 앱 계정 이용 중 | 계정 정리 때 함께 파기, 본인 계정 외 비공개 |
| 가입 미완료 Auth 사용자·세션 | 생성 후 24시간 내 정리를 운영 목표로 함 | 앱 계정 생성 여부 재검사·진행 중 정리 표시·동일 사용자 잠금으로 bootstrap 경합 차단 |
| 활성·완료·보관 목표·칭찬 | 계정 이용 중, 별도 삭제 전 | 목표 정리·계정 삭제 |
| 휴지통 목표 | 삭제 후 30일 | 기한 후 정리, 계정 삭제는 우선 적용 |
| 취소 칭찬 | 본문·실천일은 취소 즉시 제거, 상태 이벤트는 목표와 함께 보관 | 목표·계정 정책에 따른 정리 |
| 앱 내 소식 | 90일 | 만료·대상 삭제·수신자 탈퇴 |
| 최소 접근·오류·감사 로그 | 30일 | TTL 정리, 탈퇴 관련 식별 정보 정리 |
| 요청 결과 | 대상 결과가 남아 있고 작성자가 삭제되지 않은 동안 | 결과 정리 또는 작성자 삭제. 보존하는 praise FK 의존은 명시적으로 처리 |
| 재인증 grant | 만료 후 최대 24시간 | 세션·계정 삭제 시 우선 제거 |
| rate_usage | 버킷 종료 후 최대 48시간 | 계정 삭제 시 우선 제거 |
| 소비·폐기·만료 초대/종결 요청 | 종결 후 30일, 활성 연결에 필요 없는 참조 정리 | 요청·초대 FK 순서 준수 |
| 일일 DB 백업 | 7일 | 공급자 자동 정리 확인 |
| 별도 암호화 백업 | 30일 | 접근 제한 저장소에서 만료 삭제 |
| 최신 삭제 원장·완료 작업 최소 메타데이터 | 실제 정리 완료부터 최소 37일 | 백업 최대 보관 30일+7일 여유, 미완료 작업은 완료까지 유지 |

최신 삭제 원장은 복원 대상 DB와 독립적인 접근 제한 저장소에 둔다. 목적·대상 UUID/ID·정리 시각·처리 상태·만료 시각만 기록하고 본문·이메일은 넣지 않는다. 보관 위치·암호화·접근자·만료 삭제는 서비스 개설 때 재현 가능한 설정으로 확정한다.

복원은 외부 접근·메일 발송을 차단한 별도 DB에서 수행하고, 복원본보다 최신인 원장의 계정/목표/본문 파기 이력을 재적용한 뒤 검증한다. 정리된 본문과 식별자가 다시 공개되지 않음을 확인하기 전에는 서비스로 연결하지 않는다. 30일을 넘긴 별도 백업은 보관·복원 대상으로 유지하지 않는다.

원장 보관 기간은 실제 최장 백업 보관보다 반드시 길어야 한다. 백업 기간을 바꾸면 원장 만료와 복원 검증을 함께 바꾼다. 백업 생성·교체로 실제 잔존 기간이 늘어나는 설정도 검증한다.

## 데이터 정리 시 필수 검증

TC-DELETE-001~004에 목표 복구 기한·권한 미복구, 작성자 삭제·수신자 삭제, 중간 실패·재시도, 복원 후 삭제 재적용을 기록한다. 이 파일은 처리 요구이며 아직 실제 파기·백업 복원 결과는 아니다.

법령상 별도 보관이 실제로 필요한 데이터가 도입되면 목적·항목·근거·기간·접근 범위를 별도로 기록하고 공개 정책에 반영한다. 현재 무료 MVP에 결제·거래 기록 보관을 임의로 추가하지 않는다.

## W06-D1 DB 구현 상태 (2026-10-08)

목표 소프트 삭제·휴지통 조회·복구, 수신자 소식 최소 목록·읽음 처리, 관계 해제 뒤 보낸 peer 칭찬 목록과 만료 목표 파기 worker의 DB RPC를 구현했다. 이는 SQL/RLS/RPC 계층의 상태다. 대응하는 Next.js 서버 API·화면은 아직 연결하지 않았으며 OpenAPI에 그 상태를 따로 표시한다.

목표 파기 worker는 전용 비로그인 역할·service worker 호출과 독립 삭제 원장 UUID 참조를 요구한다. 기본 설정에서 원장 gate는 꺼져 있다. `OPS-INPUT-02`의 저장소 위치·암호화·만료·접근이 확정되기 전에는 스테이징/운영에서 gate를 열 수 없다. 로컬 통합 검사는 외부 원장을 생성하지 않았고, gate 거부를 먼저 확인한 뒤 폐기 가능한 로컬 DB에서 합성 참조로 정리 순서만 검증했다. 실제 파기 운영과 백업 복원 수락은 미실행이다.
