# 계정 삭제 뒤 로컬 전체 복원 연습

2026-11-11 / W14-C2a / REQ-010·NFR-001·NFR-004 / POL-DELETE-002·003

`./scripts/project.ps1 -Task db:account-restore-test`는 실제 로컬 Auth에서 합성 사용자 2명을 만들고, 목표·칭찬을 업무 RPC로 저장한 뒤 삭제 전 DB 전체를 백업한다. 실제 삭제 작업자가 한 계정의 앱 데이터와 Auth를 지운 다음, 과거 백업을 다른 임시 DB에 복원하고 DB 밖 최신 원장을 재적용한다. 검사 결과는 [보고서](../quality/reports/w14-c2a-account-restore-check-2026-11-11.json)에 기록한다.

## 실행 경계

로컬 프로젝트·고정 Node·loopback DB/API·로컬 Docker 검사를 먼저 통과해야 한다. 원본은 로컬 `postgres`로 고정한다. 대상 이름은 실행마다 `chagokchan_restore_`와 32자리 난수로 생성하며 외부 호스트나 임의 DB 이름을 받지 않는다. 원본 DB 위에 복원하지 않는다. 임시 DB에는 실행별 소유 표식을 남기고 그 표식이 일치할 때만 DROP한다. 운영 DB·전체 Docker 초기화·기존 볼륨 삭제를 수행하지 않는다.

PostgreSQL 17.11 `pg_dump --format=custom`으로 스키마·제품 데이터·Auth·migration metadata를 포함한다. 클러스터 전역 역할은 기존 로컬 클러스터에 존재하며 이번 백업에 포함하지 않는다. 역할까지 잃은 클러스터 전체 재해 복구를 검증한 것은 아니다. 복원은 단일 트랜잭션·오류 즉시 중단을 적용한다.

원래 NOLOGIN 함수 소유권을 보존하기 위해 임시 대상에만 기존 로컬 `supabase_admin` 복원 관리자를 사용한다. 원본 postgres에 추가 역할 전환 권한을 부여하거나 `--no-owner`로 함수 소유권을 바꾸지 않는다. 복원 전후 클러스터 역할 정보의 해시도 비교한다. 이 로컬 전용 방식은 관리형 운영 DB에서 사용할 수 있는 복원 명령이 아니다. 관리형 전환은 Supabase CLI의 내부 스키마/예약 역할 필터와 실제 대상 권한을 따로 검증한다. [공식 복원 문서](https://supabase.com/docs/guides/self-hosting/restore-from-platform)

## 암호화와 삭제 이력

백업은 별도 난수 키·난수 IV의 AES-256-GCM으로 암호화한다. AAD를 백업 목적·출처·정확한 snapshot 시각에 묶는다. 다른 키·출처·시각·변조·잘린 파일은 복호화하지 않는다. 현재 도구의 입력 상한은 64MiB이며 이 상한을 넘는 백업을 지원한다고 주장하지 않는다. 암호화 파일만 Git 제외 `.cache`에 잠시 저장하고 평문 dump는 프로세스 메모리에서만 다룬다. 원장 키·백업 키는 별도이며 실행 종료 시 파일과 임시 DB를 정리한다. 실제 운영 보관 주기·키 복구·30일 외부 저장소를 구성한 것은 아니다.

복원 직후 과거 계정·Auth 세션·프로필·목표·본문이 존재함을 먼저 확인한다. 독립 암호화 원장의 대상과 완료·37일 보관 정보를 확인한 뒤 복원 DB에 해당 삭제 요청을 재구성하고 기존 파기 RPC를 적용한다. 복원 DB의 Auth 행 제거는 격리된 복원 관리 작업이다. 운영 Auth API를 복원 DB에 연결하거나 Google 로그인을 수행하지 않는다. 일반 요청에 가상 JWT나 관리 키를 사용하지 않는다.

재적용 후 대상의 Auth·세션·앱 계정·프로필·목표·칭찬·grant가 0인지 확인한다. 별도 계정의 목표와 칭찬은 남아야 하며 복원된 취소 세션은 DB guard에서 거절한다. 이 DB guard 검사는 관리자 SQL로 제공한 세션 메타데이터를 사용하며 실제 제공자 로그인 수락이 아니다. 복원 DB에는 웹/API·메일·주기 작업을 연결하지 않는다.

## 완료 범위와 다음 조건

7개 로컬 통합 검사와 4개 암호화 단위를 통과했다. 약 1.02MiB의 합성 데이터 백업에서 백업 446ms·복원 1,419ms·원장 재적용 1,144ms를 관측했다. 사용자 규모·네트워크·운영자 대응을 포함한 운영 RTO나 자동 24시간 RPO를 검증한 값은 아니다. 원본 제품/private 데이터·기존 Auth 사용자/세션·키·gate·역할 보존과 임시 산출물 제거를 확인했다.

호스팅 백업/스케줄·외부 저장/키 복구·운영 Auth/설정 복원·전체 클러스터 역할 재구축·목표만 파기한 경우·칭찬 취소 내용·접수 직후 원장 기록 실패·복원 뒤 작업자 재개/원장 ACK 정합성은 남아 있다. 실제 공개 전에 이 경계를 포함한 호스팅 복원 수락이 필요하며 TC-DELETE-004는 not_run으로 유지한다. [작업자 기반](deletion-worker.md) · [진행표](backlog.md)
