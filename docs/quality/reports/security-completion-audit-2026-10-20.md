## 발견해 수정한 항목

1. **공식 보안 권고 영향 버전 사용.** Next.js 16.4.0은 이미지 최적화 및 `use cache` 관련 권고의 영향 버전이다. 공식 수정 버전 16.4.1을 포함하는 16.4.2로 정확히 고정하고 잠금 파일을 갱신했다. 이 앱에서 공격을 재현하거나 침해 흔적을 발견했다는 의미는 아니다. `use cache` 사용은 없고, 아이콘 생성은 고정된 내부 값만 받는다. 배포 플랫폼·기능 사용에 따른 도달 조건은 권고별로 다르다. 이번 npm 레지스트리 감사는 **수정 전후 모두 0건**을 반환했으므로 자동 감사만으로 영향 여부를 판단하지 않았다. [이미지 최적화 권고](https://github.com/vercel/next.js/security/advisories/GHSA-2464-fhr4-w9xw), [use cache 권고](https://github.com/vercel/next.js/security/advisories/GHSA-673q-mjm6-r5xr), [16.4.2 릴리스](https://github.com/vercel/next.js/releases/tag/v16.4.2).
2. **설계된 CSP 미적용.** 요청마다 서버가 생성한 256비트 nonce를 Next.js 렌더링과 응답 CSP에 적용했다. 호출자가 보낸 nonce/CSP를 덮어쓰며, 운영 모드의 인라인 스크립트·이벤트 핸들러·eval·외부 API 연결·프레임·object·base 삽입을 제한한다. 모든 문서를 동적으로 렌더링하고 no-store로 보낸다. 개발 디버깅에만 eval과 loopback HMR을 허용한다. 공통 no-referrer·기기 권한 제한·운영 HSTS도 추가했다. [Next.js 공식 적용 방식](https://nextjs.org/docs/app/guides/content-security-policy).

CSP의 제한된 예외는 기존 숫자 진행 막대의 React style 속성(`style-src-attr 'unsafe-inline'`)과 정적 오프라인 문서의 고정 스타일이다. 스크립트 인라인 허용은 아니다. 서비스 워커의 동일 출처 정적 파일 fetch를 유지한다. 앞으로 CAPTCHA를 연결할 때는 필요한 출처를 검토하고 실제 브라우저에서 다시 검증해야 한다. HSTS는 현재 호스트만 대상으로 하며 미정인 하위 도메인·preload를 설정하지 않았다.

CI에 공개 의존성 감사와 실제 production 빌드의 HTTP 보안 헤더 검사를 추가했다. 레지스트리 감사가 공식 권고 검토를 대체하지 않는다는 한계는 유지된다.

## 검사와 확인 범위

- 고정 Node/pnpm 환경의 lint·타입·단위 검사 175개, 산출물 구조·링크 검사, Next.js 16.4.2 production build-check를 통과했다.
- production 빌드를 격리된 loopback 포트에서 실행해 HTTP 7항목을 통과했다. 위조 nonce/CSP 덮어쓰기, 모든 Next.js script 태그와 응답 nonce 일치, 매 요청 nonce 변경, no-store·보안 헤더, 무인증 제품 API 401, 서비스 워커·오프라인 정적 정책을 확인했다. 실제 HTTPS 브라우저의 CSP 집행·화면 hydration·PWA 오프라인 수락 검사는 수행하지 않았다.
- 로컬 PostgreSQL 52개 마이그레이션의 전체 DB 검사 390개와 Auth 발급 세션 어댑터 5항목, 태그 HTTP 17항목을 통과했다. 기존 데이터·세션 보존 및 합성 검사 데이터 정리를 확인했다. 실제 Google/OTP 검사는 0건이다.
- 실제 카탈로그에서 제품 18테이블 모두 강제 RLS, API 역할의 직접 테이블/컬럼 권한 0건, 익명 SECURITY DEFINER 실행 0건, 안전하지 않은 검색 경로·슈퍼유저/로그인 소유자 0건을 확인했다. Auth 읽기·집계·삭제 전용 비로그인 BYPASSRLS 역할의 함수 13개는 별도 확인했다. 해당 역할을 API 역할이 맡을 수 없고, 고정 경로·좁은 grants·업무/작업자 내부 검사를 사용한다. BYPASSRLS 자체가 없다는 판정은 아니다.
- 일반 요청의 관리 키 거절, Auth 사용자와 DB의 현재 세션·활성 계정 검사, Origin/CSRF·JSON/32KB 제한, 응답 필드 제한, 개인/공유 권한과 캐시 경계를 검토했다. 직접 HTML 삽입이나 브라우저 Supabase 클라이언트 사용은 소스에서 발견하지 않았다.
- 추적 파일과 로컬에서 도달 가능한 Git blob 이력에 제한된 비밀 패턴 검사를 실행했다. 개인 환경·인증서·덤프 경로 및 해당 패턴 발견은 0건이었다. 공개 빌드 자산도 로컬 합성 비밀번호 및 SDK/관리 키 표식과 비교했다. 검사 수치는 JSON에 기록한다. 패턴 검사는 모든 비밀의 부재를 보증하지 않으며, 접근하지 못한 운영 자격증명·원격 전용/도달 불가능 이력·GitHub 보안 경고는 검사 범위가 아니다.

## 공개 전 해결해야 할 보안 조건

실제 로그인/OTP·PKCE·코드 재사용 방지·초대 복귀, 갱신 경합·현재/전체 로그아웃·재인증·탈퇴, 실제 계정 A→B의 PWA 캐시 수락이 남아 있다. DB의 로컬 세션 폐기 검사는 제품 로그아웃 UI/엔드포인트 완료를 뜻하지 않는다.

DB 업무 제한은 구현됐지만, 여러 서버에 걸친 API/OTP 제한·CAPTCHA·제한 저장소 장애 시 중요 쓰기 차단은 통합되지 않았다. TC-RATE-001은 미실행이며 공개 전 필수다. 독립 삭제 원장·정리 작업 경합·백업 복원·운영 비밀 분리/MFA·모니터링·로그 비식별화·실제 HTTPS/CDN 헤더와 캐시도 배포 환경에서 검증해야 한다. TC-WEB-001/002·TC-CACHE-001 등 전체 수락을 이번 부분 검사로 통과 처리하지 않았다.

이번 Codex 직접 검토에서 확인한 수정 항목은 해결했으나, 이 미구현·미검증 조건 때문에 **현재 공개 출시 판정은 보류**다.
