# 로그인, 계정 연결, 칭찬판 권한

결정일: 2026-10-07 / 상태: 구현 정책 결정

기술 기준: [개발 스택](technical-architecture.md). 로그인 제공자 연결과 서비스 안에서 다른 사람과 연결하는 기능은 따로 관리한다.

2026-10-08 사용자 결정: 개발 중에는 로그인 화면 없이 [로컬 가상 사용자](development/local-development.md)로 이용한다. 아래 로그인 정책은 출시 기준이며 실제 제공자 연동·로그인 테스트·실사용은 오픈 준비 때 수행한다. 계정 UUID·DB 세션·RLS·판 권한 검사는 로컬에서도 유지한다.

## 로그인 결정

| 항목 | 결정 |
| --- | --- |
| 인증 운영 | Supabase Auth |
| 첫 로그인 수단 | Google OAuth + 이메일 6자리 인증번호 |
| 비밀번호 | 첫 버전에서 직접 수집하지 않음 |
| 사용자 식별 | Supabase 사용자 UUID. 이메일·닉네임은 사용자 ID로 쓰지 않음 |
| 세션 전달 | 동일 출처 서버 API, 서버 관리 HttpOnly 쿠키 |
| Google 인증 | Authorization Code + PKCE, Supabase SDK의 검증 흐름 사용 |
| 이메일 인증번호 | 10분 유효, 재발송 60초 간격, 검증 시도 제한 |
| 접근 토큰 | JWT 만료 15분으로 설정 |
| 전체 세션 | Pro Auth의 최대 30일·7일 비활동 만료 설정, 여러 기기 사용 허용 |
| 로그아웃 | 현재 기기 로그아웃과 모든 기기 로그아웃을 분리 |
| 민감 작업 | 계정 삭제·로그인 수단 변경에는 10분 이내 재인증 요구 |

위 시간과 제한은 이 제품에서 정한 초기 정책이다. Supabase 기본값을 그대로 적은 값이 아니다. 사용자 테스트·운영 관찰로 바꾸면 결정 기록과 설정을 함께 변경한다. [OTP 설정](https://supabase.com/docs/guides/auth/auth-email-passwordless), [세션 설정](https://supabase.com/docs/guides/auth/sessions)

Google에 가입한 이메일과 동일한 주소로 이메일 OTP 로그인을 하면 Supabase의 검증된 identity 정책에 따라 같은 계정으로 접근하게 한다. 이 동작과 미확인 이메일의 거절을 스테이징에서 검증한다. 앱 자체가 이메일 문자열만 비교하여 계정을 병합하지 않는다.

재인증은 새 인증번호 검증 또는 로그인 제공자의 재인증 흐름으로 수행하고 기존 사용자 UUID와 일치하는지 확인한다. 확인한 시각과 작업 범위를 서버가 기록한다. JWT 갱신이나 화면 확인 버튼만으로 재인증 시간을 늘리지 않는다.

다른 이메일의 계정 병합과 수동 identity 연결 화면은 후속 기능으로 둔다. Kakao·Apple 등 추가 제공자는 별도 출시 단계에서 연결·복구·기존 계정 유지 정책을 확인한다. Supabase의 수동 identity linking은 현재 문서에서 beta로 안내된다. [Identity Linking](https://supabase.com/docs/guides/auth/auth-identity-linking)

## 서버 세션과 쿠키

브라우저는 로그인 시작·OTP 검증·로그아웃을 앱 서버에 요청한다. 서버가 Supabase Auth를 호출하고 로그인 토큰을 서버가 읽는 쿠키로 설정한다. 브라우저에서는 Supabase Auth 클라이언트를 만들지 않고 모든 제품 데이터 요청을 앱 API로 보낸다.

- 운영 쿠키: Secure, HttpOnly, SameSite=Lax, Path=/, Domain 속성 생략. 개발용 HTTP 예외는 localhost로 제한한다.
- 서버 Auth 쿠키 기본 이름은 grape_auth이며 SDK의 분할 이름을 함께 관리한다. 실제 고정 SDK 버전에서 쿠키·PKCE·갱신을 확인한다. [API 계약](contracts/api-contract.md)
- OAuth의 인증 결과는 서버 콜백에서 세션으로 교환한다. 콜백 코드를 브라우저 저장소나 로그에 남기지 않는다.
- 세션 토큰을 URL, JSON 응답, localStorage, 클라이언트 로그로 반환하지 않는다.
- 서버 SDK에서 쿠키 분할·갱신을 처리하고, 병렬 요청 시 갱신 경합·만료·여러 기기 로그아웃을 테스트한다.
- 인증 응답·쿠키 갱신 응답에는 no-store를 적용한다.
- next 경로는 같은 서비스의 허용된 상대 경로만 받아 열린 리다이렉트를 막는다.

이는 브라우저와 서버가 모두 토큰을 읽는 Supabase 기본 SSR 예제를 그대로 사용하는 방식과 다르다. HttpOnly 정책이 유지되도록 인증·갱신을 서버에 일원화한다. [서버 인증 가이드](https://supabase.com/docs/guides/auth/server-side/advanced-guide), [서버 전용 쿠키 조건](https://supabase.com/docs/guides/auth/sessions)

검증된 JWT만으로 최신 사람 연결 권한을 결정하지 않는다. DB에서 사용자 상태와 해당 session_id의 존재, 현재 연결·차단·판 참여 상태를 확인한다. 세션 확인은 현재 세션의 유효 여부만 반환하는 비공개 보조 함수로 수행한다. 로그아웃 이후 JWT가 만료 전까지 남을 수 있기 때문에 이 확인을 보호 데이터의 읽기와 쓰기에 적용한다. 세션 기간 제한이 갱신 시 적용되는 동작도 검증한다. [Supabase 세션과 로그아웃](https://supabase.com/docs/guides/auth/sessions)

## 로그인 처리 흐름

### Google

로그인 선택 → 서버가 PKCE 인증 URL과 검증용 쿠키 준비 → Google·Supabase 인증 → 허용된 앱 콜백 → 서버에서 code 교환·사용자 확인 → 세션 쿠키 설정 → 기존 active 계정은 내 목표·원래 목적지, 신규 사용자는 가입 확인 화면으로 이동.

OAuth 제공자의 Supabase 콜백 URL과 Supabase에서 앱으로 돌아오는 URL은 별도로 등록한다. 운영·스테이징의 프로젝트·OAuth 자격증명·콜백 목록을 분리한다. 운영에서는 정확한 HTTPS 주소를 허용한다.

### 이메일 인증번호

이메일 입력 → Turnstile와 요청 제한 확인 → 같은 안내 문구 표시 → 인증 메일 → 사용자가 6자리 번호 입력 → 서버가 OTP 검증 → 사용자 확인·세션 쿠키 설정 → 기존 active 계정은 내 목표·원래 목적지, 신규 사용자는 가입 확인 화면으로 이동.

‘이 이메일에 계정이 있는지’는 발송 응답으로 공개하지 않는다. 메일 소유를 검증한 사용자가 가입 또는 기존 계정 접근을 진행한다. 운영 메일은 Resend Custom SMTP와 검증된 발신 도메인을 사용한다.

### 최초 앱 가입

새 Auth 사용자는 아직 제품 접근 권한이 없다. /signup의 만 19세 이상 자기 확인과 현재 정책 버전을 제출한 뒤 bootstrap RPC가 앱 계정·프로필·최초 확인 기록을 한 트랜잭션에서 만든다. 확인 누락·false·버전 불일치와 직접 호출 우회를 검사한다. 기존 로그인과 재시도는 최초 기록을 덮어쓰지 않는다. 생년월일·전화 본인확인·신분증 수집은 없으며 실제 연령 검증 완료로 표시하지 않는다. [성인 가입 정책](policies/audience-and-signup.md)

## 다른 사용자와 연결하는 방법

첫 버전은 **일회용 초대 링크·QR·입력 코드**로 연결한다. 이메일·전화번호로 전체 사용자 목록을 검색하는 기능은 제공하지 않는다.

| 초대 정보 | 결정 |
| --- | --- |
| 링크 비밀 | CSPRNG로 만든 24바이트 난수, base64url로 표현 |
| 입력 코드 | 12자리 Crockford Base32, 60비트 난수, 구분용 하이픈 허용 |
| 보관 | 원문 대신 SHA-256 해시, 발급자·만료·상태 보관 |
| 유효 기간 | 발급 후 24시간 |
| 사용 횟수 | 연결 요청 한 건에 한 번 사용 |
| 생성 제한 | 계정당 활성 초대 5개, 하루 발급 20개 |
| 사용 조건 | 로그인, 유효한 초대 확인, 명시적인 연결 요청 |
| 최종 연결 | 초대한 사람이 요청자의 닉네임을 확인하고 수락 |
| 요청 만료 | 요청 생성 후 48시간 |
| 초대 권한 | 사람 연결만 요청. 어떤 목표의 권한도 자동 부여하지 않음 |

링크는 /connect#invite=... 형태로 비밀을 fragment에 넣는다. 브라우저가 읽고 로그인 이후 명시적인 POST로 제출한다. 임시 보관이 필요하면 해당 탭의 sessionStorage에만 두고 처리·취소 시 지운다. 초대 화면에는 외부 분석 스크립트를 넣지 않고 Referrer-Policy: no-referrer, no-store를 적용한다.

GET, 링크 미리보기, QR 스캔만으로 연결을 완료하거나 초대를 소모하지 않는다. 링크 비밀을 알더라도 로그인과 발급자의 최종 확인을 거쳐야 하며 공유판 권한은 추가로 필요하다. 짧은 코드는 링크보다 비밀 길이가 짧으므로 조회·사용에 계정·IP별 제한을 적용한다.

### 연결 순서

1. A가 초대를 만들고 원하는 사람에게 직접 링크·QR·코드를 전달한다.
2. B가 로그인하고 A의 최소 표시 정보만 확인한 뒤 연결 요청을 보낸다.
3. 서버가 자기 자신, 차단된 관계, 만료·폐기·이미 사용한 초대를 거절한다.
4. A가 B를 확인해 수락하면 연결 상태가 active가 된다.
5. A 또는 B가 자기 목표의 공유판에서 상대에게 칭찬 권한을 준다.

두 사용자 연결은 순서를 정규화한 사용자 ID 쌍으로 중복을 막는다. 양방향 동시 요청과 수락은 하나의 활성 관계로 처리한다. 연결·공유를 해제했다가 다시 연결해도 과거 판 권한을 자동 복구하지 않는다.

## 첫 버전 권한표

첫 버전의 제품 역할은 ‘목표 주인’과 ‘칭찬할 수 있는 지인’이다. 보기 전용·공동 관리·그룹 역할은 확장 후보로 유지한다.

| 작업 | 목표 주인 | 연결만 된 사람 | 해당 공유판의 칭찬 권한자 | 관계없는 사용자 |
| --- | --- | --- | --- | --- |
| 개인 목표 원본·개인 메모 보기 | 허용 | 거절 | 거절 | 거절 |
| 개인 포도알 부여·수정·취소 | 허용 | 거절 | 거절 | 거절 |
| 공유판 공개 제목·진행 개수 보기 | 허용 | 거절 | 허용 | 거절 |
| 공유판에 셀프 칭찬 부여 | 거절, 개인판 사용 | 거절 | 해당 없음 | 거절 |
| 지인의 공유판에 칭찬 부여 | 주인 자신은 거절 | 거절 | 활성 목표에 허용 | 거절 |
| 공유판의 받은 칭찬 전체 본문 보기 | 허용 | 거절 | 자기 칭찬만 허용 | 거절 |
| 자신이 보낸 칭찬 취소 | 자기 기록이면 허용 | 별도 본인 기록 경로 | 허용 | 자기 작성 기록만 별도 경로 |
| 다른 사람이 보낸 칭찬 내용 편집 | 거절 | 거절 | 거절 | 거절 |
| 받은 칭찬 숨기기·개수 제외 | 허용 | 거절 | 거절 | 거절 |
| 목표·판·회차 설정 변경 | 허용 | 거절 | 거절 | 거절 |
| 공유 대상·권한 변경 | 허용 | 거절 | 거절 | 거절 |
| 수신 소식 확인·읽음 변경 | 수신자 본인만 | 본인 소식만 | 본인 소식만 | 본인 소식만 |

같은 공유판에 참여한 지인이 다른 지인의 칭찬 본문을 자동으로 읽게 하지 않는다. 지인에게는 공유용 표시 정보, 전체 진행 개수, 자신이 보낸 칭찬만 제공한다. 개인 포도알의 개수와 실제 목표의 개인 설명도 자동으로 공개하지 않는다.

## 연결 해제·차단·칭찬 취소

- 어느 한쪽이 연결 해제하면 연결과 해당 관계의 판 참여 권한을 비활성화한다. 이후 공유판 조회·부여를 거절한다.
- 차단하면 양쪽의 연결·초대·새 칭찬을 중단한다. 차단 여부를 알리는 별도 메시지는 상대에게 보내지 않는다.
- 공유판 주인이 특정 지인의 권한만 해제할 수도 있다. 사람 연결 자체와 다른 판 권한은 별도로 관리한다.
- 받은 칭찬은 관계가 끝나도 주인의 기록으로 유지한다. 주인은 숨기기 또는 개수 제외를 할 수 있다.
- 작성자는 관계 해제 후에도 별도 ‘보낸 칭찬’ 경로에서 본인이 작성한 내용만 확인·취소할 수 있다. 이 경로는 상대의 현재 목표 정보, 진행 개수, 다른 칭찬을 제공하지 않는다.
- 받은 칭찬 숨기기는 본문 노출을 줄이고 개수는 유지한다. 개수 제외는 유효 개수에서 제외한다. 작성자의 취소는 별도 상태로 관리한다.

권한 회수는 이후 서버 요청과 DB 접근을 차단하는 방식으로 보장한다. 이미 전달된 화면·캡처까지 회수할 수 있다고 설명하지 않는다. 화면 복귀와 데이터 재조회에서는 최신 권한을 확인하고 접근 불가 상태로 바꾼다.

## DB·API 강제 조건

공유 칭찬의 허용 조건은 로그인·활성 계정·활성 세션 AND 공유판 AND 주인과 다른 작성자 AND 활성 연결 AND 양쪽 모두 차단 없음 AND 해당 판 참여 권한 AND 진행 중 목표다.

개인 칭찬은 로그인·활성 계정·활성 세션 AND 개인판 AND 목표 주인 본인 AND 진행 중 목표로 제한한다. 수신자와 판의 소유자는 서버와 DB가 판 레코드에서 정한다.

공유 해제·연결 해제와 신규 칭찬 처리에는 일관된 잠금 순서를 사용한다. 함수별 실행 권한, 직접 테이블 변경 거절, 위조한 사용자 ID, RLS·뷰·RPC 직접 호출을 모두 테스트한다. [RLS 동작](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 요청 제한 초기값

아래는 서비스 정책이다. Supabase Auth 자체 제한과 함께 적용한다.

| 요청 | 초기 제한 |
| --- | --- |
| 이메일 OTP 발송 | 이메일당 60초 간격·1시간 5회, IP당 1시간 20회 |
| OTP 검증 | 이메일·브라우저 흐름별 10분 5회, IP별 10분 30회 |
| 초대 조회·사용 | 계정당 15분 10회, IP당 15분 30회 |
| 연결 요청 | 계정당 하루 20회 |
| 칭찬 부여 전체 | 개인·공유 합계 계정당 분당 20회, 하루 300회 |
| 같은 공유판 칭찬 | 같은 작성자·수신자·판 조합당 하루 30회 |

칭찬 수정·취소·숨김·제외는 별도 계정당 분당 60회 제한을 적용하며 일일 부여 300회 한도에는 포함하지 않는다. 이미 성공한 업무의 재시도는 새 부여로 세지 않는다.

중복 요청 키의 재시도는 같은 칭찬을 새로 만들지 않는다. Data API를 직접 호출해도 중요한 사용자별 쓰기 제한은 DB에서 적용한다. 이메일 인증 자체는 Supabase의 CAPTCHA·요청 제한도 켠다. [Auth 제한](https://supabase.com/docs/guides/auth/rate-limits), [CAPTCHA 지원](https://supabase.com/features/auth-captcha-protection)

운영자의 Supabase·Vercel·GitHub 계정은 MFA를 필수로 사용하고 제품 사용자 역할과 구분한다. 사용자의 개인 기록을 읽는 운영자 기능은 첫 버전에 넣지 않는다. DB 관리 자격증명은 별도 관리 권한이므로 비밀키 최소화·감사 기록·접근 통제로 보호한다.
