# 추가 고려사항과 결정 우선순위

작성일: 2026-10-07 / 상태: 추가 검토 목록과 권장안

기준 문서: [제품 기획](product-plan-v0.2.md), [기술 아키텍처](technical-architecture.md), [로그인·권한](auth-and-permissions.md), [보안](security-threat-model.md), [배포·Git](deployment-and-git.md).

개인·공유 포도송이 분리, 목표별 생성, 지인의 공유 칭찬, 개발 스택은 기존 결정을 따른다. 이 문서의 ‘권장안’은 추가 제안이다. 구현 정책으로 채택할 때 해당 기획·기술 문서에도 반영한다.

우선 구체화할 부분은 **기록의 삭제·탈퇴 처리**, **초대에서 첫 칭찬까지의 경험**, **혼자 쓰는 가치와 지인 칭찬의 가치를 확인할 지표**다.

실제 개발 작업의 선행 결정·API·검증 조건은 [구현 전 고려사항](pre-implementation-plan.md), 데이터 관계와 키 설계는 [ERD v0.3](data-erd.md)에 구체화했다. 아래 권장안의 후속 개발 기준은 [정책 JSON](../policies/app-policy.json)과 [제품 규칙](policies/product-rules.md), [생명주기](policies/data-lifecycle.md)에 기록했다. 기존 미정 표시는 탐색 당시 상태이며 현재 기준은 해당 정책 파일을 따른다.

## 1. 첫 사용자와 제품 경험

포도 스티커의 그림은 성인·아이·가족이 모두 사용할 수 있지만 화면·가입·공유 기본값은 사용자층에 따라 달라진다. 첫 베타는 성인 개인이 운동·독서·작은 성취를 기록하고 가까운 지인에게 칭찬받는 상황으로 확정했다. 어린이·교사·부모 사용은 별도 후보로 관리한다.

대표 사용자에게 제공할 첫 경험은 ‘목표 하나 만들기 → 나를 한 번 칭찬하기’다. 지인을 연결하지 않아도 쓸 수 있어야 한다. 첫 화면에서 친구 초대·모든 설정·PWA 설치를 한꺼번에 요구하지 않는다.

한국 첫 가입 기준은 만 19세 이상 자기 확인으로 정했다. 생년월일·전화 본인확인은 수집하지 않는다. 상세는 [가입 정책](policies/audience-and-signup.md)을 따른다. 향후 아동·보호자 계정을 확장할 경우에는 별도 검토가 필요하다. 국내에서 만 14세 미만 아동의 개인정보 처리에 법상 동의가 필요한 경우 법정대리인의 동의와 확인이 요구된다. 아동 계정을 포함한다면 보호자 계정과 아이 계정의 관계, 누가 누구의 기록을 읽는지, 독립 계정 전환도 함께 설계한다. [개인정보 보호법 제22조의2](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1020398523)

## 2. 기록 삭제·탈퇴·복구

권한 해제와 개인정보 삭제는 다른 처리다. 기존의 연결 해제 정책만으로 목표 삭제나 계정 탈퇴 이후의 기록 처리가 정해지지는 않는다.

| 상황 | 기존 결정 | 추가로 정할 부분·권장안 |
| --- | --- | --- |
| 지인 연결·공유 권한 해제 | 이후 판 조회·새 칭찬 거절, 받은 기록 유지 | 보낸함에서 자기 기록만 읽는 예외를 화면에도 설명 |
| 보낸 칭찬 취소 | 해당 회차 개수 감소, 이후 회차 기록 유지 | 취소 전 영향을 표시하고 내용 없는 취소 상태 안내를 권장 |
| 받은 칭찬 숨기기·제외 | 숨기기는 개수 유지, 제외는 개수 감소 | 메뉴명·확인 안내를 구분하고 제외 복구 가능 여부 결정 |
| 목표 보관 | 새 칭찬 입력 중단 | 본인 조회·재개 동작과 지인 화면의 상태 안내 정의 |
| 목표 삭제 | 미정 | 개인·공유 기록, 상대의 보낸함, 소식의 삭제 범위를 함께 결정. 우선 보관을 쉽게 제공 |
| 칭찬 작성자 탈퇴 | 미정 | 작성자 표시·본문·포도알 개수를 각각 결정. 본문 제거·작성자 연결 제거·기여 이벤트 유지안을 검토 |
| 목표 주인 탈퇴 | 미정 | 본인 목표·기록 삭제와 상대 보낸함의 처리, 연결·초대·소식 정리 범위 정의 |
| 탈퇴 후 재가입 | 미정 | 새 계정으로 시작하고 과거 연결·판 권한을 자동 복구하지 않는 안 권장 |
| 백업 복원 | DB 백업 7일, 별도 내보내기 30일 기준 | 삭제된 사용자·기록이 다시 공개되지 않도록 삭제 이력 재적용 절차 필요 |

작성자가 탈퇴해도 개수를 유지하는 안을 채택한다면, 삭제한 본문을 다시 읽거나 취소하는 기능과는 분리해야 한다. 기여 이벤트에 남길 정보·처리 목적·보관 기간을 먼저 정하고, UUID만 남긴다고 익명 데이터가 된다고 가정하지 않는다.

삭제 요청은 재인증 → 접근 중단·세션 폐기 → 연결·기록 처리 → 작업 완료 확인 순서로 설계한다. 반복 요청·중간 실패에도 안전하게 이어서 처리해야 한다. 원본 DB, 로그, 백업, 추후 파일 저장소별 처리 시점도 공개 정책과 맞춘다.

탈퇴 전 데이터 내려받기를 제공할지 검토한다. 초기 내보내기는 본인 개인 기록과 받은 기록 중 허용된 정보만 대상으로 하고, 지인의 이메일·비공개 프로필·다른 판 정보는 포함하지 않는다. 목표 삭제의 복구 기간과 탈퇴 철회 기간은 아직 정하지 않았으므로 화면에서 복구를 약속하지 않는다.

## 3. 목표·회차·날짜 규칙

- **목표 개수 변경:** 20알 중 15알을 모은 회차를 10알로 바꿨을 때의 혼란을 줄이기 위해 새 개수는 다음 회차에 적용하는 안을 권장한다. 첫 회차 생성 전에는 수정 가능하게 한다.
- **목표 완료와 포도송이 완성:** 실제 목표 완료 시 개인·공유판의 신규 부여를 함께 닫고, 진행 중인 포도송이는 현재 상태로 보관하는 안을 검토한다. 재개 시 기존 회차를 이어갈지 명시한다.
- **칭찬 수정:** 개인 메모의 내용 수정, 공유 칭찬 문구 수정, 취소를 구분한다. 문구 수정으로 포도알이 추가되거나 원래 작성자가 바뀌지 않게 한다.
- **칭찬 제외 복구:** 받은 칭찬을 제외했다가 되돌릴 때 완료 상태·소식·배지를 어떻게 처리할지 결정한다. 재완성으로 보상을 반복 받지 않게 확장 규칙을 준비한다.
- **날짜와 시간대:** 서버 부여 시각은 UTC로 저장하고 표시 시간대는 사용자 설정으로 관리하는 안을 권장한다. 한국어 첫 출시의 초기 표시값은 Asia/Seoul로 제안한다.
- **과거 실천 입력:** 허용한다면 실천일과 칭찬을 기록한 시각을 분리한다. 실천일 변경이 서버의 하루 부여 제한을 우회하지 않게 한다.
- **설정 상한:** 포도알 목표 개수, 활성 목표 수, 연결 수, 판별 참여자 수의 상한을 정하고 최대값의 화면·조회 성능을 검증한다.

이 결정은 개인·공유 개수의 분리를 바꾸지 않는다. 기간형 목표·수치 목표·하루 한 번 규칙은 별도 출시 단계에서 추가한다.

## 4. 초대·로그인·계정 복구

초대받은 사람에게는 ‘누가 나를 초대했는지’, ‘연결하면 무엇이 보이는지’, ‘아직 칭찬 권한이 없는 이유’를 단계에 맞게 설명한다. 로그인 후에는 초대 흐름으로 돌아오고, 만료된 링크는 새 초대를 받는 동작으로 안내한다.

초대한 사람의 수락 화면에서 공유할 목표를 명시적으로 함께 선택할 수 있게 하면 별도 설정 화면을 찾는 부담을 줄일 수 있다. 사람 연결만 수락하는 선택도 유지한다. 초대 자체가 판 권한을 자동 부여하도록 바꾸지는 않는다.

카카오톡·다른 메신저의 인앱 브라우저 → Google 또는 이메일 로그인 → 초대 복귀를 실제 휴대폰에서 검증한다. 외부 브라우저로 열면 기존 탭의 임시 초대 정보가 이어지지 않을 수 있으므로 전체 초대 링크·입력 코드로 다시 시작하는 경로를 제공한다.

Google은 개발자가 통제하는 임베디드 브라우저에서 OAuth 인증 요청을 보내는 것을 제한한다. 모든 인앱 브라우저가 같은 방식으로 동작한다고 가정하지 않고, 실패 시 외부 브라우저 열기·코드 입력을 안내한다. 로그인 목적에 필요한 최소 scope만 사용한다. [Google OAuth 정책](https://developers.google.com/identity/protocols/oauth2/policies)

Google 공개 서비스 준비에는 앱 이름·소유 도메인·홈페이지·개인정보처리방침·이용약관 링크가 필요하다. 브랜드·동의 화면·공개 상태와 필요한 검증 절차를 출시 일정에 포함한다. 캘린더·주소록 등 추가 접근 권한은 기능을 도입하는 시점에 별도로 다룬다. [Google 공개 앱 정책](https://developers.google.com/identity/protocols/oauth2/policies)

계정 복구는 ‘기존 이메일을 검증할 수 있음’, ‘Google 계정에만 접근 가능’, ‘둘 다 잃음’으로 나눠 정의한다. 새 이메일·같은 닉네임·칭찬 내용만으로 이전 계정을 넘겨주지 않는다. 운영자의 임의 이메일 변경이나 UUID 병합을 지원하지 않는다면 그 제한도 안내한다.

## 5. 개인정보와 운영 주체

출시할 서비스의 운영 주체, 사용자 연락 창구, 처리방침·이용약관을 정한다. 실제 수집값은 이메일·인증 식별자·닉네임·목표·칭찬·연결·운영 기록 수준으로 목록화하고, 각 항목의 목적·접근자·보관·삭제 시점을 기록한다. 주소록·전화번호·정확한 생년월일 등 추가 정보는 필요한 기능이 생길 때 검토한다.

서울 DB를 선택해도 로그인·메일·CDN·Redis·오류 추적의 처리 위치는 각각 확인해야 한다. 서비스별 데이터 흐름을 작성하고 실제 국외 처리·보관이 있다면 적용 근거와 안내·동의 방식을 정한다. 국외 이전의 요건은 실제 처리위탁·보관·제공 방식에 따라 검토한다. [개인정보 보호법 제28조의8](https://law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1020398611)

개인정보처리방침은 실제 운영 설정과 일치하게 작성한다. 선택적인 분석·마케팅 수집은 핵심 로그인·칭찬 이용과 구분한다. 개인정보보호위원회의 2026년 작성지침을 후속 문서 작성 기준으로 활용한다. [개인정보 처리방침 작성지침](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS217&mCode=D010000000&nttId=12018)

사용자가 불편한 칭찬을 숨기고 상대를 차단하는 기존 기능에 더해, 문제를 문의·신고할 최소 경로를 준비한다. 운영자가 개인판 전체를 읽지 않아도 문제를 처리할 수 있게 사용자가 선택한 대상 기록·요청 ID만 제출하는 방식을 검토한다. 신고로 보관하는 정보와 기간은 일반 칭찬 보관과 따로 정의한다.

## 6. 접근성·알림·오류 경험

| 상황 | 권장 경험 |
| --- | --- |
| 공유 칭찬이 아직 없음 | 개인판은 바로 사용할 수 있게 하고 초대 설명은 선택적으로 표시 |
| 포도알 색을 구분하기 어려움 | 개인/받은 칭찬 제목·아이콘·개수로 함께 구분 |
| 포도 그림 조작이 어려움 | 같은 기록의 목록 보기, 큰 버튼, 키보드·스크린리더 접근 |
| 큰 글자·작은 화면 | 긴 목표·닉네임·칭찬 문구가 잘리지 않고 필요한 부분을 읽을 수 있게 함 |
| 움직임을 줄이고 싶음 | 완료 애니메이션을 줄이고 결과 안내는 유지 |
| 완료 직후 이전 칭찬 취소 | 어느 회차가 바뀌는지 안내하고 다음 회차 기록은 그대로 표시 |
| 전송 결과를 받지 못함 | 전송 확인 중·성공·실패를 구분하고 같은 요청 키로 안전하게 재시도 |
| 오프라인·메일 지연 | 온라인 필요·재전송 대기 시간을 안내하고 성공을 미리 표시하지 않음 |
| 권한·초대 만료 | 원문 기술 오류 대신 접근 불가·새 초대 받기·로그인하기 등 다음 행동 제공 |

첫 버전은 앱 내 소식을 유지하고, 기기 푸시와 리마인더는 후속 검증 항목으로 둔다. 이후에는 칭찬 수신·연결 요청·완성·리마인더를 따로 설정하고, 묶음 알림·조용한 시간·잠금 화면 본문 숨김을 검토한다.

iOS/iPadOS의 Web Push는 16.4부터 홈 화면에 추가한 웹 앱에 지원되며 사용자의 직접 행동에 따른 권한 요청이 필요하다. 푸시를 추가할 때 실제 지원 기기·설치 상태·권한 거절을 검증하고 앱 내 소식 경로를 유지한다. [WebKit Web Push 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

칭찬을 못 받은 날의 공개 비교·순위·독촉은 첫 버전에 넣지 않는 안을 권장한다. 공유 칭찬이 적어도 자기 기록의 가치를 느낄 수 있는지, 연속 기록·완료 표현이 부담을 주는지 베타에서 확인한다.

## 7. 비용·성능·운영 책임

월 운영비는 웹·DB의 기본 비용, 스테이징 프로젝트, 메일, Redis, 도메인, 로그·백업을 합산해 기록한다. 공급자 요금은 개설 시 확인하고 베타·정식 운영 예산을 구분한다. 현재 문서에는 미확인 금액을 넣지 않는다.

사용 규모는 가정 사용자 수·활성 비율·하루 칭찬 수·공유판 조회 수·OTP 발송 수로 계산한다. 첫 용량 검증은 예상 베타 규모와 그보다 큰 동시 요청 시나리오를 사용한다. 판·회차·작성자·수신자·날짜 기반 인덱스, 페이지 조회, 권한 확인 비용을 함께 측정한다.

사용량 제한 초과와 비용 알림 발생 시 누가 조치할지 정한다. 메일 장애, 로그인 장애, DB 쓰기 장애의 사용자 안내와 지원 연락처를 준비하고, 기존 [배포·복원 절차](deployment-and-git.md)에 연결한다.

초대 응답·칭찬 쓰기 같은 핵심 API의 오류율과 처리 시간을 관찰한다. 새 기능으로 비용·쿼리·보관 데이터가 늘어나면 예산과 상한을 함께 조정한다. 서비스 종료 시 데이터 내보내기·삭제·도메인과 백업 종료 순서도 운영 정책에 포함한다.

## 8. 베타 검증과 성공 지표

앱 실행 횟수 외에 실제 칭찬 기록과 연결 결과를 확인한다. 첫 실험은 혼자 사용하는 사람과 지인 한 쌍으로 사용하는 사람을 포함하는 소규모 2주 베타로 제안한다. 참여자 모집이나 연락은 아직 수행하지 않았다.

| 지표 | 정의·사용 목적 |
| --- | --- |
| 첫 셀프 칭찬 도달률 | 가입한 테스트 사용자 중 목표 생성 후 첫 개인 칭찬을 남긴 비율 |
| 첫 기록까지의 시간 | 목표 생성·로그인에서 막히는 단계 확인 |
| 7일 재기록률 | 첫 셀프 칭찬 이후 1~7일의 다른 날에 다시 기록한 사용자 비율. 관찰 7일이 지난 집단만 계산 |
| 연결 완료율 | 명시적인 초대 사용 시도 → 연결 요청 → 수락으로 이어진 비율 |
| 첫 공유 칭찬 전환 | 판 권한을 받은 지인 중 실제 칭찬을 한 사람의 비율 |
| 권한 설정 실패·문의 | 사람 연결과 판 공유의 차이를 사용자가 이해하는지 확인 |
| 전송 오류·중복·신고 | 제품 사용을 방해하는 문제와 불편한 관계 처리 확인 |

연결 전환은 개인정보를 읽을 수 없는 단순 링크 미리보기 GET을 사용자의 연결 시도로 세지 않는다. 셀프 칭찬과 공유 칭찬의 지표도 합산하지 않는다.

분석 이벤트는 목표 생성·셀프 칭찬·명시적 연결 요청·연결 수락·권한 부여·공유 칭찬 정도로 시작한다. 목표 제목·칭찬 본문·이메일·초대 비밀은 분석 도구로 보내지 않는다. 사용자 ID를 포함한다면 개인정보 처리 목록에 넣고 분석 보관 기간을 정한다.

베타 통과 기준은 기능이 동작하는지와 사용자가 다시 기록하고 싶은지를 함께 본다. 실제 결과를 얻기 전에 재방문율·칭찬 효과·시장성을 입증한 것으로 표현하지 않는다. 베타 결과를 바탕으로 다음 한두 기능과 개선을 선택한다.

## 9. 후속 확장 도입 조건

| 확장 | 도입을 검토할 근거 | 추가로 준비할 정책 |
| --- | --- | --- |
| 수익화 | 무료 베타에서 재사용·가치 확인 | 유료 범위·환불·해지·결제 수단. 기본 기록·삭제·보안 기능은 유지하는 안 권장 |
| 네이티브 앱·위젯 | PWA 사용 중 설치·입력·플랫폼 제약이 반복 확인됨 | 모바일 세션·스토어 출시·동기화·기기 권한 |
| 그룹·공동 목표 | 한 사람의 목표 공유와 다른 공동 사용 요구가 확인됨 | 소유자·역할·탈퇴·기여 귀속·삭제 범위 |
| 보상·배지 | 회차 완성 경험의 추가 가치 확인 | 취소·재완성·중복 보상·조건 변경 |
| 사진·댓글·공개 공유 | 텍스트 칭찬 이상의 맥락이 필요하다는 사용 근거 | 업로드·신고·외부 공개·파일 삭제·사진 메타데이터 |
| AI·외부 연동 | 직접 문구 작성·실천 기록에서 반복되는 필요 확인 | 보내는 데이터·외부 제공자·권한 회수·사용자 문구 확정 |

확장할 때 기존 기록과 개인·공유 권한을 보존하는 원칙은 [기능 확장 설계](feature-expansion-design.md)를 따른다. 새 기능별 사용 근거와 추가 정책을 해당 변경 문서·PR에 남긴다.

## 다음 결정 순서

2. 목표·회차·날짜 규칙과 초대·판 선택의 전체 화면 흐름을 구체화한다.

4. 접근성·오류·알림 시나리오와 베타 지표를 개발 검증에 포함한다.
5. 베타 결과로 수익화와 후속 확장의 순서를 결정한다.
