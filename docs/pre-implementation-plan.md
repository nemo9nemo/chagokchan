기준: [제품 기획](product-plan-v0.2.md), [추가 고려사항](additional-considerations.md), [개발 스택](technical-architecture.md), [데이터 ERD](data-erd.md).

## 1. 구현 범위와 우선순위

첫 버전은 계정·프로필, 목표별 개인판, 선택적인 공유판, 지인 연결·판별 권한, 칭찬·취소·숨기기·제외, 앱 내 소식, 지난 포도송이를 구현한다. 목표 실천량과 개인·공유 칭찬 개수는 각각 관리한다.

첫 개발에서 사용할 경계는 Next.js 서버 API → 사용자 세션의 Supabase 읽기/RLS → 업무 변경 RPC다. 브라우저는 서버 API로만 제품 데이터를 요청한다. 테마·그룹·AI·사진·네이티브·푸시는 후속 기능의 도입 조건을 관리한다.

| 개발 단위 | 코드 작성 전에 준비할 것 | 완료 판단 |
| --- | --- | --- |
| DB·권한 | ERD, 외래키·유일성·공개 범위, 삭제 정책, 트랜잭션 순서 | 허용·거절·동시성 시나리오를 설명할 수 있음 |
| 인증 | Google·OTP 흐름, 서버 쿠키, 현재 세션 확인, 재인증 | 로그인·갱신·현재/전체 로그아웃을 같은 기준으로 구현 가능 |
| 개인 기록 | 목표·판·회차 상태, 날짜와 설정 변경 규칙 | 부여·취소·완성·재개가 서로 모순되지 않음 |
| 연결·공유 | 초대 사용·요청·수락·권한 부여·차단 상태 | 두 사용자 흐름과 무권한 사용자의 거절 결과가 정해짐 |
| 화면·소식 | 핵심 화면, 빈 상태·오류·접근성, 조회 범위 | 개인·공유·전송 상태와 다음 행동이 분명함 |
| 배포 | 로컬·스테이징·운영 분리, 설정·비밀·마이그레이션 | 같은 소스를 환경에 맞게 검증·배포할 수 있음 |

## 3. DB에서 반드시 지킬 조건

1. 한 목표는 한 사람에게 속한다. 첫 버전에는 개인판 1개와 선택적인 공유판 1개를 둔다.
2. 칭찬은 한 판의 한 회차에 속한다. 수신자는 해당 판의 주인이고 개인·공유 알을 이동·합산하지 않는다.
3. 신규 개인 칭찬의 작성자는 주인, 신규 공유 칭찬의 작성자는 허용된 다른 사용자다.
4. 공개 프로필과 계정 상태·설정, 개인 목표 원본과 공유 표시 정보를 분리한다.
5. 연결과 차단·판 권한은 현재 DB 상태를 검사한다. 클라이언트의 사용자 ID·역할·개수로 권한을 결정하지 않는다.
6. 같은 작성자·작업·요청 키는 한 번만 처리한다. 같은 키로 입력이 달라지면 충돌로 거절한다.
7. 칭찬·개수·회차 완성·소식·중복 요청 결과를 같은 트랜잭션으로 기록한다. 실패 시 전부 반영되지 않아야 한다.
8. 진행 개수는 취소되지 않고 제외되지 않은 칭찬의 개수와 일치한다. 숨김은 집계를 바꾸지 않는다.
9. 권한 해제·차단·탈퇴 접근 중단과 기록 쓰기는 일관된 잠금 순서로 처리한다. 먼저 완료된 기록과 이후 거절된 요청을 구분한다.
10. 과거 회차 취소로 개수가 줄어도 현재 회차의 기록을 옮기지 않는다. 불완전한 지난 회차가 있을 수 있다.

외래키·유일 제약으로 보장할 것과, 현재 연결 상태처럼 RPC 안에서 확인할 것을 구분한다. 다른 행의 상태를 단순 CHECK 함수에 넣어 계속 보장되는 제약으로 취급하지 않는다. [PostgreSQL 제약 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)

## 4. API 계약을 먼저 작성할 범위

아래 표는 /api/v1 기준의 요약이다. 현재 요청·응답·오류·경로의 기준은 [OpenAPI 계약](../contracts/openapi.json)과 [API 규칙](contracts/api-contract.md)이다.

| 기능 | API 설계안 | 핵심 계약 |
| --- | --- | --- |
| 내 계정·설정 | GET /me, PATCH /me | 본인 정보만, 공개 프로필 응답과 구분 |
| 목표 | GET/POST /goals, PATCH /goals/:id | 본인 소유, 변경 시 revision 확인 |
| 목표 보관·재개 | POST /goals/:id/archive 또는 resume | 상태 전이·신규 칭찬 허용 여부 명시 |
| 공유판 생성 | POST /goals/:id/shared-board | 주인만, 공유 제목·설명 별도 입력 |
| 판 조회 | GET /boards/:id | 주인용·지인용 응답 필드 분리 |
| 칭찬 부여 | POST /boards/:id/praises | 요청 키 필수, 작성자·수신자·회차는 서버/DB가 결정 |
| 칭찬 정리 | POST /praises/:id/cancel, hide, exclude | 동작별 역할·집계 영향 구분 |
| 초대·연결 요청 | POST /connection-invites, /connection-requests | 비밀 검증·1회 사용·요청 만료, GET은 상태 변경 없음 |
| 연결 수락·거절 | POST /connection-requests/:id/accept 또는 reject | 초대한 사람만, 같은 관계의 중복 활성화 방지 |
| 판 권한 | PUT/DELETE /boards/:id/members/:userId | 주인만, 활성 연결 필요, 명시적인 판 선택 |
| 연결 해제·차단 | DELETE /connections/:id, POST /blocks | 이후 판 접근·새 부여 거절, 받은 기록 정책 유지 |
| 소식·보낸함 | GET /notifications, /sent-praises | 소식은 수신자만, 보낸함은 본문과 최소 정보만 |
| 계정 삭제 | POST /account/deletion-requests | 재인증, 접근 중단, 정해진 삭제 정책, 중복 요청 안전성 |

소유·작성자·집계 필드는 변경 입력에서 제외한다. PATCH에서 임의 필드를 저장하는 방식은 사용하지 않는다. revision이 있는 객체는 오래된 화면의 수정으로 최신 설정을 덮어쓰지 않도록 충돌을 반환한다.

중복 칭찬 재시도는 같은 praise_id를 반환한다. 진행 개수 화면은 최신 데이터로 재조회하며 오래된 전송 결과의 개수를 현재 값으로 덮어쓰지 않는다. 오류에는 요청 ID와 안정적인 오류 코드를 제공하고 개인 본문·토큰을 포함하지 않는다.

| HTTP 상태 | 의미·예시 |
| --- | --- |
| 400 | 입력 검증 실패 |
| 401 | 로그인 필요·세션 종료 |
| 404 | 없거나 접근할 수 없는 객체. 비공개 객체의 존재를 확인해 주지 않음 |
| 403 | 이미 볼 수 있는 객체에서 해당 행동 권한이 없음 |
| 409 | 요청 키 재사용의 다른 입력·revision 불일치·현재 상태에서 불가능한 전이 |
| 429 | 요청 제한, 재시도 가능 시각 안내 |
| 503 | 일시 장애·중요 요청의 제한 저장소 장애 |

## 5. 인증·권한 구현 전에 검증할 것

2026-10-08 사용자 결정에 따라 개발 중에는 [로컬 가상 사용자](development/local-development.md)의 세션으로 DB·업무 권한과 API를 먼저 검증하고 화면을 구현한다. 실제 Google PKCE 콜백, OTP 검증, HttpOnly 쿠키 분할·갱신, 동시 요청, 로그인 후 초대 복귀, 현재/전체 로그아웃은 오픈 준비 때 연동·검증한다. 로컬 사용자 검사를 실제 인증 성공으로 대체하지 않는다.

읽기에는 활성 계정·현재 세션·RLS, 변경에는 위 조건과 RPC 내부 역할 검사를 적용한다. 일반 요청에 service role을 사용하지 않는다. 권한 상승 함수의 소유자·search_path·실행 역할·조회 필드를 문서화한다.

특히 세 가지 읽기 경로를 분리한다: 주인의 개인 목표 원본, 지인의 공유판 정보, 연결 해제 후 본인의 보낸 칭찬. 지인 권한을 확인하기 위해 개인 목표 전체를 API에 반환하지 않는다. 현재 규칙과 상세 검증은 [로그인·권한](auth-and-permissions.md), [보안 출시 기준](security-threat-model.md)을 따른다.

## 7. 의미 있는 초기 검증 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| A의 개인 7알·공유 3알에 셀프 칭찬 | 개인만 8알 |
| 허용된 B가 A에게 칭찬 | 공유만 4알, A의 소식 1건 |
| 같은 요청을 여러 번 전송 | 칭찬·개수·소식 각각 한 번만 반영 |
| 같은 요청 키로 다른 판·내용 전송 | 409, 추가 반영 없음 |
| 마지막 알에 서로 다른 두 요청 | 하나는 기존 회차 완성, 다음은 새 회차에 1회 반영 |
| B에게 연결만 있고 판 권한 없음 | 공유판 조회·부여 거절 |
| C가 ID를 바꿔 A의 개인판·B의 본문 조회 | API·DB 직접 호출 모두 거절 |
| 공유 해제·차단과 칭찬 동시 처리 | 정한 잠금 순서대로 완료, 해제 커밋 후 새 요청 거절 |
| 관계 해제 후 B의 보낸함 조회 | B 본인 내용만, A의 현재 개수·개인 정보 없음 |
| 이전 완료 회차 칭찬 취소 | 이전 회차만 감소, 이후 회차 기록·현재 포인터 유지 |
| 받은 칭찬 숨기기·제외 | 숨기기는 개수 유지, 제외는 감소 |
| 로그아웃·탈퇴 접근 중단 후 기존 JWT | 보호 데이터 접근 거절 |
| A 로그아웃 후 같은 기기에서 B 로그인 | A의 캐시·개인 기록 노출 없음 |
| 초대 동시 사용·수락·만료 | 한 초대는 한 요청, 한 관계는 한 활성 연결 |
| 단위 작업 중간 오류 | 일부 칭찬·개수·소식만 남지 않음 |

권한과 기록 트랜잭션은 DB 수준에서, 사용자 흐름·기기·캐시는 E2E로 검증한다. 단순 화면 문자열이나 구현과 같은 계산을 복사한 테스트보다 허용·거절·동시성 결과를 검증한다. 현재는 검증 요구를 작성한 단계다.

## 8. 실제 구현 시작 순서

1. I01~I09의 정책 파일·ERD·계약·TC를 같은 기준으로 확인한다. 기준 파일은 현재 생성한 상태다.
2. 로컬 앱·DB 환경을 만들고 사용자·목표·판·회차의 마이그레이션과 권한부터 작성한다.
3. 로컬 가상 사용자 세션과 서버 API 경계를 연결하고 현재 DB 세션·권한 확인을 검증한다. 사용자 로그인 입력은 요구하지 않는다.
4. 개인 칭찬의 중복·집계·취소·완성을 구현한다.
5. 연결·차단·판 권한과 공유 칭찬을 구현한다.
6. 소식·보낸함·계정 삭제 작업·PWA·접근성을 연결한다.
7. 오픈 준비 때 실제 로그인 제공자·가입·세션을 연동하고 스테이징에서 실제 로그인·여러 계정 권한·보안·복원을 검증한 뒤 출시한다.

도메인·예산·브랜드 같은 공개 출시 준비는 로컬 개발과 병행할 수 있다. DB 키와 기록 삭제 동작을 바꾸는 결정은 해당 구현 전에 정리한다.
